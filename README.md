# Indian ETF and Mutual Fund Backtesting and Advisory API

This project provides a robust, dockerized backend system for backtesting investment strategies for Indian ETFs and Mutual Funds, and offering daily investment advice. It is built with FastAPI, SQLAlchemy, PostgreSQL, and Docker, following a clean, modular architecture.

## 1. Architecture Overview

The system employs a layered and modular architecture to ensure separation of concerns, maintainability, and scalability.

-   **API Layer (FastAPI):** Handles incoming HTTP requests, routing, and response serialization.
-   **Service Layer:** Contains core business logic, orchestrating interactions between CRUD operations, external data sources, and strategy engines.
-   **CRUD Layer:** Provides an abstraction for database operations (Create, Read, Update, Delete) for SQLAlchemy models.
-   **Database Layer (SQLAlchemy ORM + PostgreSQL):** Defines ORM models and manages database sessions.
-   **Strategy Layer (Pure Python):** A completely decoupled module containing the backtesting and advisory algorithms, free from API or DB dependencies.
-   **Data Abstraction Layer:** Manages interaction with external financial data providers, including caching mechanisms.
-   **Containerization (Docker):** Ensures consistent development, testing, and production environments.

## 2. Features

-   **User Authentication:** Register and log in users with JWT-based authentication.
-   **Backtest Engine:** Simulate investment strategies (RSI + MA20 with SIP, dip buying) on historical ETF/MF data.
-   **Daily ETF/MF Advisor:** Provides daily buy/sell recommendations based on market conditions.
-   **Symbol Discovery:** Search and cache ETF, Mutual Fund, and Benchmark Index symbols.

## 3. Technology Stack

-   **Backend Framework:** FastAPI
-   **ORM:** SQLAlchemy (2.0 style)
-   **Database:** PostgreSQL (Production), SQLite (Local Testing)
-   **Migrations:** Alembic
-   **Authentication:** JWT (email + password, bcrypt hashing)
-   **Testing:** Pytest
-   **API Documentation:** OpenAPI/Swagger UI (auto-generated by FastAPI)
-   **Containerization:** Docker, `docker-compose`
-   **Data Sources:** `nsepython`, `jugaad-data`, `mfapi.in`
-   **Utilities:** `pydantic-settings`, `python-jose`, `passlib`, `bcrypt`, `python-dotenv`, `requests`, `numpy`, `pandas`, `numpy_financial`

## 5. Setup Instructions

### Prerequisites
-   Docker and Docker Compose
-   Python 3.10+
-   `pip` (Python package installer)

### Local Development (without Docker - using virtual environment)

1.  **Clone the repository:**
    ```bash
    git clone https://github.com/your-username/ETF-Strategy-basic.git
    cd ETF-Strategy-basic
    ```
2.  **Create and activate a virtual environment:**
    ```bash
    python3 -m venv venv
    source venv/bin/activate
    ```
    *Note: If `python3 -m venv venv` fails on Debian/Ubuntu, you might need to install `python3-venv`: `sudo apt install python3.10-venv`.*

3.  **Install dependencies:**
    ```bash
    pip install -r requirements.txt
    ```
4.  **Set up environment variables:**
    Copy `.env.example` to `.env` and adjust as needed.
    ```bash
    cp .env.example .env
    ```
    Ensure `DATABASE_URL` in `.env` points to your local PostgreSQL or SQLite database. For SQLite (for testing): `DATABASE_URL="sqlite:///./test.db"`
    For PostgreSQL: `DATABASE_URL="postgresql://user:password@localhost:5432/etf_backtest"` (replace `user`, `password`, `localhost`, `etf_backtest` with your actual values)

5.  **Initialize Alembic (if not already done):**
    ```bash
    alembic init alembic
    ```
    *Note: `alembic/env.py` and `alembic/script.py.mako` might need manual setup based on the project structure. This project has these files pre-configured.*

6.  **Run migrations:**
    ```bash
    alembic revision --autogenerate -m "Initial migration"
    alembic upgrade head
    ```
7.  **Run the FastAPI application:**
    ```bash
    uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
    ```
    The API documentation will be available at `http://127.0.0.1:8000/docs`.

## 6. Docker Usage

### Build and run with Docker Compose
1.  **Ensure Docker is running.**
2.  **Set up environment variables:**
    Create a `.env` file in the project root (if not present) based on `.env.example`.
    The `DATABASE_URL` in `.env` should point to the `db` service:
    `DATABASE_URL="postgresql://user:password@db:5432/etf_backtest"`
    `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` in `.env` should match the environment variables used by the `db` service in `docker-compose.yml`.

3.  **Build and start the services:**
    ```bash
    docker-compose up --build -d
    ```
    This will start the `db` (PostgreSQL) and `backend` (FastAPI) services in detached mode.

4.  **Run database migrations within the backend container:**
    ```bash
    docker-compose exec backend alembic upgrade head
    ```

5.  **Access the API:**
    The FastAPI application will be accessible at `http://localhost:8000/docs`.

### Stopping Docker services
```bash
docker-compose down
```

## 7. Database Migrations

This project uses Alembic for database migrations.

### Configuration
The `alembic.ini` file configures Alembic. Ensure `sqlalchemy.url` is correctly set, typically using an environment variable as defined in `.env`.

### Generating a new migration
After making changes to SQLAlchemy models in `app/db/models.py`:
1.  **Ensure your virtual environment is active (if not using Docker for commands).**
2.  **Generate the migration script:**
    ```bash
    alembic revision --autogenerate -m "Description of your changes"
    ```
    Review the generated script in `alembic/versions/` and modify if necessary.
3.  **Apply the migration:**
    ```bash
    alembic upgrade head
    ```
    If running inside Docker: `docker-compose exec backend alembic upgrade head`

## 9. Strategy Explanation

The core investment strategy implemented is a combination of a monthly Systematic Investment Plan (SIP) and a tactical "dip-buying" strategy based on the Relative Strength Index (RSI) and 20-day Moving Average (MA20).

**SIP Logic:**
- A fixed `sip_amount` is invested monthly on the first 5 days of the month.

**Dip-Buying Logic:**
- **Indicators:**
    - **RSI (14-period):** Measures the speed and change of price movements. A reading below 30 typically indicates an oversold condition.
    - **MA20 (20-day Moving Average):** A short-term trend indicator.
- **Buy Condition:** When the instrument's 14-period RSI falls below 30 *AND* its current closing price is below its 20-day Moving Average, a "dip-buy" is triggered.
- **Buy Amount:** The amount purchased during a dip is `sip_amount * dip_multiplier`. This allows for larger investments during perceived dips.
- **Cash Management:** Funds accumulated from uninvested SIP amounts (if `carry_over_fraction` is enabled, though currently not fully implemented in cash management beyond simple SIPs) can be used for dip buying.

**Output:**
The backtest generates an equity curve, a benchmark curve (if a benchmark is provided), a list of all transactions, and summary statistics including absolute returns and XIRR.

## 10. Assumptions

-   **Data Availability:** Assumes `nsepython`, `jugaad-data`, and `mfapi.in` provide reliable and sufficient historical data.
-   **SIP Frequency:** Monthly SIP assumed to occur on the first few trading days of the month.
-   **RSI Period:** Default RSI period is 14.
-   **MA Period:** Default MA period is 20.
-   **Benchmark Type:** Assumes benchmark indices are of `INDEX` type for data fetching.
-   **MF NAV:** For Mutual Funds, NAV is used as the `close`, `open`, `high`, `low`, and `adjusted_close` price. Volume is considered 0.
-   **Symbol Search:** MFAPI symbol search is currently implemented by fetching all and filtering, which is not scalable for very large lists in a live API call. Pre-caching all MF symbols would be a more robust solution.

-   **XIRR Calculation:** The current `calculate_xirr` uses `numpy_financial.irr` which is a simplified IRR calculation and does not fully account for dates in the same way a true XIRR (Extended Internal Rate of Return) function (e.g., from `scipy.optimize.newton`) would. This should be refactored for more accuracy.
-   **Data Gaps:** The backtest and advisor logic might behave unpredictably with significant data gaps or holidays not properly handled by external data sources or `ffill`/`bfill` strategies.
-   **Error Handling (External APIs):** Limited specific error handling for various failure modes of `nsepython`, `jugaad-data`, and `mfapi.in` (e.g., rate limits, invalid symbols, API changes).
-   **Performance:** For very long backtesting periods or large numbers of instruments, performance might degrade without further optimizations (e.g., vectorized operations, database query tuning, parallel processing).
-   **Carry-over Logic:** The `carry_over_fraction` is part of the strategy input but its full implications on cash management for future investments are not thoroughly implemented in the `backtest_engine.py` beyond basic SIP and dip buying.
-   **Transaction Saving:** The backtest results (equity curves, transactions) are calculated but not yet persisted to the `backtest_results` or `transactions` tables in the database.
-   **Real-time Data:** The system relies on historical data and "yesterday's close" for advisory. Real-time data integration is not in scope.
